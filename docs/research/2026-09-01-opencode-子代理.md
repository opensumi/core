# OpenCode 子代理 — 研究笔记

**研究对象：**[OpenCode 官方中文文档：代理](https://opencode.ai/docs/zh-cn/agents/#%E5%AD%90%E4%BB%A3%E7%90%86)（重点为“子代理”） **资料范围：**OpenCode 官方文档、其发布的 [JSON 配置 Schema](https://opencode.ai/config.json) 与 [官方文档源文件](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/zh-cn/agents.mdx)。以下结论描述文档当前所述行为，并非对某个本地安装版本的保证。

## 核心结论

OpenCode 将代理分为直接承载用户主对话的 `primary` 与供其委派专门工作的 `subagent`。主代理可依据子代理的 `description` 自动委派；用户也能以 `@代理名` 直接发起。子代理的“能否做什么”不是由 `subagent` 标签本身决定，而是由模型、工具/权限、任务权限与嵌套深度共同决定。

来源：[代理类型与调用方式](https://opencode.ai/docs/zh-cn/agents/#%E7%B1%BB%E5%9E%8B)、[模式](https://opencode.ai/docs/zh-cn/agents/#%E6%A8%A1%E5%BC%8F)、[配置 Schema：`AgentConfig`](https://opencode.ai/config.json)。

## 角色及适用场景

官方内置三种子代理：

- **General**：研究复杂问题、执行多步骤任务；除 `todo` 外具有完整工具访问，因此必要时可改文件，也适合并行处理多个工作单元。
- **Explore**：快速、只读地探索代码库；用于查找文件、关键字、模式及回答代码库问题，不能修改文件。
- **Scout**：只读地研究外部文档和依赖；可将依赖仓库克隆到 OpenCode 托管缓存、检查库源码或同 upstream 实现交叉对照，而不改工作区。

这三个名称是默认角色，并非强制的安全等级：自定义子代理可拥有不同的提示词、模型、权限和工具。设计新角色时，应先以职责写清 `description`（文档称其为必填），再选择最小权限，而非把 `subagent` 误解为天然只读或天然可写。

来源：[内置 General / Explore / Scout](https://opencode.ai/docs/zh-cn/agents/#%E5%86%85%E7%BD%AE%E4%BB%A3%E7%90%86)、[描述](https://opencode.ai/docs/zh-cn/agents/#%E6%8F%8F%E8%BF%B0)、[官方 Schema 中的 `description` 与 `mode`](https://opencode.ai/config.json)。

## 调用与会话关系

主代理会按子代理描述自动调用适合的角色；用户也可在消息中使用 `@general` 一类的提及直接调用。子代理创建子会话后，可用 `session_child_cycle` / `session_child_cycle_reverse`（默认快捷键分别为 `<Leader>+Right` / `<Leader>+Left`）在父会话与各子会话之间切换。

来源：[用法：自动调用、`@` 调用和会话导航](https://opencode.ai/docs/zh-cn/agents/#%E7%94%A8%E6%B3%95)。

## 配置方式与 Markdown frontmatter

可在 `opencode.json` 的 `agent` 对象中定义或覆盖代理，也可用 Markdown 定义。Markdown 文件放在全局 `~/.config/opencode/agents/` 或项目 `.opencode/agents/`；文件名就是代理名，例如 `review.md` 生成 `review`。frontmatter 承载配置，正文则是该代理的系统提示词。

一个面向代码审查的最小示例如下（字段可同写入 JSON）：

```markdown
---
description: 只读审查代码，报告风险与改进建议
mode: subagent
model: anthropic/claude-sonnet-4-20250514
temperature: 0.1
steps: 12
permission:
  edit: deny
  bash:
    '*': ask
    'git diff': allow
---

检查正确性、安全性和可维护性；不要修改文件。
```

`description` 用于说明功能与何时使用；`mode` 取 `primary`、`subagent` 或 `all`，未指定时默认 `all`。常用的其他字段包括：`prompt`（系统提示词或相对配置文件的 `{file:...}` 引用）、`model`、`temperature`、`top_p`、`steps`、`disable`、`color`、`tools` 与 `permission`。其中 `maxSteps` 已弃用，应使用 `steps`；达到 `steps` 上限后，代理会被要求以纯文本总结工作和剩余建议。`tools` 仍可使用，但官方 Schema 标为已弃用，建议以 `permission` 取代。

来源：[JSON 与 Markdown 配置](https://opencode.ai/docs/zh-cn/agents/#%E9%85%8D%E7%BD%AE)、[选项：描述、提示词、最大步数、禁用、颜色与 Top P](https://opencode.ai/docs/zh-cn/agents/#%E9%80%89%E9%A1%B9)、[官方 Schema：`AgentConfig`](https://opencode.ai/config.json)。

## 模型、工具和权限

代理可通过 `model: provider/model-id` 覆盖模型。若子代理未设置模型，它继承**调用它的主代理**所用模型；未设置模型的主代理则使用全局配置模型。文档还说明，配置中未识别的代理字段会作为模型选项直接传给提供商，因此如 `reasoningEffort`、`textVerbosity` 一类字段是具体模型/提供商相关的，不应假定跨提供商可用。

代理级工具配置会覆盖全局工具配置。更适合控制实际副作用的是 `permission`：官方文档举例的 `edit`、`bash`、`webfetch` 可设为 `ask`、`allow` 或 `deny`，其中 `ask` 需审批、`allow` 不需审批、`deny` 禁用。`bash` 支持 glob 规则；规则按顺序计算，**最后匹配者优先**，故通配的 `"*"` 应放在更具体规则之前。

来源：[模型](https://opencode.ai/docs/zh-cn/agents/#%E6%A8%A1%E5%9E%8B)、[工具](https://opencode.ai/docs/zh-cn/agents/#%E5%B7%A5%E5%85%B7)、[权限](https://opencode.ai/docs/zh-cn/agents/#%E6%9D%83%E9%99%90)、[其他选项](https://opencode.ai/docs/zh-cn/agents/#%E5%85%B6%E4%BB%96%E9%80%89%E9%A1%B9)、[官方 Schema：`PermissionConfig`](https://opencode.ai/config.json)。

## 控制“代理能委派给谁”

对某个调用方代理设置 `permission.task`，可按子代理名的 glob 规则控制它经 Task 工具可调用的目标。例如先将 `"*"` 设为 `deny`，再将 `"research-*"` 设为 `allow`，可形成只允许研究角色的委派面。设为 `deny` 的子代理会从该调用方看见的 Task 工具描述中移除，模型不会尝试调用它；这比仅在提示词中要求“不调用”更具约束力。

不过，`permission.task` 只限制代理通过 Task 工具委派，**不阻止用户**从 `@` 自动补全菜单直接调用子代理。`hidden: true` 仅隐藏 `mode: subagent` 代理在该菜单中的可见性；权限允许时模型仍可通过 Task 工具调用它。因此，对内部角色同时考虑 `hidden`、调用方的 `permission.task` 和目标代理自己的工具权限。

来源：[任务权限](https://opencode.ai/docs/zh-cn/agents/#%E4%BB%BB%E5%8A%A1%E6%9D%83%E9%99%90)、[隐藏](https://opencode.ai/docs/zh-cn/agents/#%E9%9A%90%E8%97%8F)、[官方 Schema：`hidden` 字段](https://opencode.ai/config.json)。

## 运行边界与实践注意事项

1. **默认不允许无限递归。** 顶层 `subagent_depth` 的默认值是 `1`，即默认阻止子代理再启动子代理；需要多层委派时必须显式提高它，且要评估成本与编排复杂度。
2. **子代理会有独立会话上下文。** 它们生成子会话，须通过导航快捷键在父/子会话间查看；不要假设它们与主会话是同一条连续对话。
3. **“只读”必须以权限落实。** General 默认可改文件，Explore 和 Scout 才是内置只读角色；自定义审查或研究角色应明确拒绝 `edit`，并按需限制 `bash`、`webfetch` 等权限。
4. **父代理受限不等于子代理受限。** 当前官方实现仅将父会话的 `deny` 与 `external_directory` 规则带入子会话；子代理自身的权限决定其能力。并且，若子代理没有自己允许相应权限，任务创建时会默认拒绝其 `todowrite` 和 `task`。因此每个子代理都应独立配置权限，且要显式放行其继续委派所需的 `task` 权限。
5. **后台委派是实验性能力。** Task 默认前台运行；只有设置 `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true` 才能以 `background: true` 运行，完成/失败后才会回传父会话。生产流程不应把后台模式当作无条件可用的默认行为。
6. **模型继承是隐式成本与质量变量。** 未固定 `model` 的子代理随调用主代理的模型变化，可能改变能力、延迟和费用；需要稳定行为时显式设置并确认该提供商/模型可用。
7. **步数上限是成本护栏，不是完成保证。** 到达 `steps` 后只会请求文本总结；编排方需能接收“不完整结果”和后续工作建议。
